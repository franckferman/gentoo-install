Why this installer

Nothing is written
before you have read it.

Every default is documented, every guard has its own switch, and every claim on this page was produced by running it.

📋

Plan before write

--dry-run prints the whole plan — the partition table, the sizes, the command line — and needs no root. It is complete by construction: every write goes through one function.

🔏

Signed stage3

The chain is walked end to end: a clearsigned pointer, a detached signature on the archive, a signed checksum file, and the byte count. Not a checksum from the same server that served the file.

🔢

Steps are the API

Eleven numbers, 10 through 95. They appear in --steps, in the docs and in your own notes, and adding one between two others does not move the rest.

⌨️

Typed proof

Erasing a disk means typing its path by hand. Neither --yes nor --force lifts that, and neither of them answers the reboot question either.

🔑

Two ways in, exercised

An encrypted install does not finish until two independent credentials have each been made to open the container — here, now, not in a comment. A TPM that stops releasing the key is an ordinary event.

🧰

Ten rescue scripts

Standalone by design: none of them sources the installer's libraries, so any one can be copied alone onto a USB stick for a machine that no longer boots.

Quick start

From a live medium,
starting with a plan.

Clone it, read what it would do, then decide.

# On the live medium
git clone https://github.com/franckferman/gentoo-install
cd gentoo-install

# What would happen on this machine, changing nothing. No root needed.
./gentoo-install.sh --dry-run

# A desktop on an encrypted disk, unlocked by the TPM
sudo ./gentoo-install.sh --disk /dev/nvme0n1 --crypt luks-tpm

# A headless server: no 32-bit ABI, /var and /var/log split off
sudo ./gentoo-install.sh --profile server --disk-layout server

# Pick up where an interrupted run stopped
sudo ./gentoo-install.sh --resume

The state journal defaults to /var/lib/gentoo-install, which on a live medium is RAM. The installer says so at startup and names --state-dir as the way to keep a journal a reboot cannot lose.

Steps

Eleven steps. Run all, or pick any.

--steps 20,40-60,95 selects; --skip-steps 75 removes. A bare number has to name a real step; a range simply selects whatever exists inside it.

10

preflight

Eleven read-only checks: privileges, firmware, architecture, tools, network, DNS, clock, disks, memory, TPM, keyring. A FAIL stops; a WARN asks.

What the encryption variant still owes the target, done inside the target — luks-tpm binds its keyslot to the chip there, with the clevis that will have to release it at every boot.

Five verdicts on the machine as it now exists — kernel, initramfs, boot entry, fstab, a way in — then the unmount and what to do next. A failed proof is not an opinion to override.

The four choices

Four decisions.
Everything else has a default.

Each is a directory of variants: adding one means adding a file, not editing a dispatcher.

Encryption
luks-passphrase
Default. Typed at every boot, and a recovery slot beside it.
luks-tpm
Sealed to the chip, recovery passphrase always kept. Needs clevis, which lives in the GURU overlay.
luks-keyfile-gpg
A long random key in a GPG envelope on the ESP: two secrets, not one.
none
Says out loud what it means.
Bootloader
grub
Default. UEFI and legacy BIOS, encrypted /boot, LVM.
uki
Kernel, initramfs and command line in one signed EFI binary. Needs no NVRAM entry at all.
systemd-boot
UEFI only. Works under OpenRC — bootctl comes from systemd-utils.
efistub
The firmware starts the kernel. The NVRAM entry is the configuration.
Kernel
dist-kernel
Default. gentoo-kernel-bin, prebuilt and signed by Gentoo.
genkernel
Compiled here, configured for you. Its own initramfs dialect.
manual
Your sources, your .config.
Disk layout
desktop
LVM; the system takes what it needs and /home takes the rest.
server
LVM with /var and /var/log split off, and a fifth of the group left free for lvextend.
minimal
One root partition. No LVM, nothing to learn.
custom
Your own table, described in the configuration file.
What it refuses

The guards, and what each one cost.

Every one of these exists because something happened. They are listed here rather than buried, because a refusal you did not expect is worth reading about before you meet it.

🔌

Firmware state

It will not write an NVRAM entry, or reboot, for a disk this machine did not boot from — unless it is running from a live medium. An install to a disk image once replaced a working laptop's own boot entry and then rebooted it.

🛑

A failed pre-flight

Its eleven checks decide whether anything may be written at all, so its failure ends the run rather than joining the others in the summary. It was accumulated like the rest until a run refused a disk for being too small and erased it anyway.

↩️

The reboot

--yes does not answer it. Only --reboot yes, written on purpose, does — a reboot is irreversible in the way a typed proof is.

🔐

One way in

An encrypted install does not report success with a single credential. A container only the TPM opens is one firmware update away from a rebuild.

🧭

A plan from another life

Resuming mounts the tree the recorded plan describes — unless that plan names the disk this machine booted from, which would mount a running system under /mnt/gentoo.

🧪

An unproved sealing

clevis luks list reads the same whether the chip honours a token or refuses it. So the chip is made to release the key, and what it hands back is tested against the keyslot.

📄

A file it did not write

Every write is a marked block, a backup, or a refusal — and the backup is compared with what is already there, so a rerun does not leave a directory of identical copies.

Status · v0.1.0

What has actually been booted.

This section is the one that matters, and it is kept honest on purpose: "tested in a VM" without naming the paths tested is the kind of claim this project exists not to make.

the installed machine, after booting from its own disk
gitpm ~ # clevis luks list -d /dev/vda2
2: tpm2 '{"hash":"sha256","key":"ecc","pcr_bank":"sha256","pcr_ids":"0,2,3,6"}'

An encrypted machine installed by this script — LVM on LUKS2, a keyslot sealed to a software TPM under QEMU with OVMF — was booted from its own disk with no ISO attached. It unlocked itself, checked four filesystems and reached a login prompt without asking for anything. An unencrypted disk was carried from an empty GPT to a login prompt earlier.

The four bootloaders, one line each. The column on the right is copied from nothing: docs/TESTING.md holds the status of record and a test refuses this page if the two disagree.

  • grub booted On an encrypted disk, through the passphrase prompt to a login.
  • efistub booted From the NVRAM entry step 80 writes, with no bootloader of any kind in between.
  • uki booted Against a firmware whose NVRAM had never heard of it: started from \EFI\BOOT\BOOTX64.EFI, where the same firmware with a GRUB install had fallen through to PXE the day before.
  • systemd-boot booted The loader's own menu — the entry step 80 wrote, counting down the timeout step 80 wrote — reached from \EFI\BOOT\BOOTX64.EFI on a firmware given a pristine variable store, because the install was refused an NVRAM entry on purpose.

What none of it covers: efistub has not been booted from the removable path — that one needs a kernel with its command line compiled in, because the fallback is launched with no load options at all. musl, hardened and llvm stages have been unpacked, and musl carried as far as step 70 — a kernel and a dracut initramfs with crypt, crypt-lib and dm in it — but no musl machine has been booted either. Read the plan before you point version 0.1.0 at a disk you would miss.
